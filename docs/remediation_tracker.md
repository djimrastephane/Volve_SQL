Architecture recommendations (Phase 4) implemented: versioned-migration workaround for a `CREATE OR REPLACE VIEW`
column rename (documented in `sql/05_views.sql`, exercised as a real upgrade against an already-populated
database — see finding 7's evidence); minimal load provenance (`sql/08_load_provenance.sql`:
`core.load_runs` + `analytics.vw_load_revision`, the latter is how the dashboard role reads a revision counter
without any core grant); a bounded, transaction-scoped load lock (`pg_advisory_xact_lock`, `_acquire_load_lock`,
live-verified to time out and fail cleanly under real contention); structured logging in `app/db.py`/`app/nlsql.py`
(categorized, never logging question/SQL text); CI hardening (`permissions: contents: read`, all GitHub Actions
pinned to reviewed commit SHAs); `requirements-runtime.txt` (deployable subset, no test/notebook tooling);
`pip-audit` run for real (found and fixed one real, low-severity dev-dependency CVE — `pytest` 8.4.2 → 9.0.3,
full suite re-verified passing); a real backup/restore drill (`pg_dump`/`pg_restore` against the disposable
cluster, `sql/04_quality_checks.sql` reporting identical counts on the restored copy) documented in
README "Backup and restore"; negative-privilege/role-attribute tests (`tests/test_privileges.py`) as the
executable form of "make privilege intent executable." Deliberately **not** implemented: materialized views,
COPY-based loading, a generic staging layer, or partitioning — no measured cost justifies them at this dataset's
size, consistent with the audit's own "the main risk is not a lack of architectural complexity" conclusion.

## Blocked / external (cannot be verified from this environment)

- **Live Docker Compose exercise of finding 1.** The Docker daemon was not running in this sandbox
  (`docker ps` → "cannot connect to the Docker API"). The password-auth/loopback-bind configuration was verified
  by review and by the equivalent pattern CI's `loader-fixture-test` job already runs live against a real
  `postgres:17` container (password-required, non-trust auth) — but the specific `docker-compose.yml` file
  itself was not launched end-to-end in this session. Recommend a manual `make docker-up` verification before
  relying on it.
- **Production deployment decisions.** Authentication/reverse-proxy in front of the dashboard, TLS for a
  remote database, a real recovery-point/recovery-time objective, and multi-user resource sizing are named
  explicitly in README "Production deployment prerequisites" as decisions this repository cannot make on a
  deploying organization's behalf — not implemented, and not claimed to be.
